## Введение

При создании приложения для миллионов пользователей и обрабатывающего десятки или даже тысячи запросов в секунду, нужно соблюдать ряд требований.
Данные требования позволяют достичь следующих целей:

1. не "упасть" при неожиданном повышении нагрузки - числа входящих запросов
2. не "положить" смежные сервисы - поставщики данных, не создавать лишнюю нагрузку на систему в целом
3. вернуть осмысленный ответ клиенту даже в случае сбоя
4. обработать максимальное число пользовательских запросов на имеющемся "железе"

Назовем эти требования паттернами надежности. Вот их список:

1. оптимальное использование памяти
2. пул потоков
3. обработка ошибок
4. Timeouts
5. Rate Limiter
6. Circuit Breaker
7. Retry
8. Fallback
9. Cache

Материалы к заданиям можно найти [тут](materials/links.md).

## Задание 0.5 Тестовый бизнес-сервис

Суть проекта - вернуть клиенту список рекомендованных игр по REST API.
Для получения списка используются 2 внешних вызова по REST:

1. вызов сервиса рекомендаций, в ответ возвращается список id игр
2. вызов сервиса игр для получения данных об игре по id, полученным от сервиса рекомендаций

### Основные шаги

1) создай структуру проекта, аналогичную "Project Backend 03", но вместо datasource - используй пакет adapter для работы с внешними сервисами. Пакет domain необязателен, т.к. наш тестовый
   сервис не содержит много бизнес-логики, можно обойтись паттерном Transaction Script и вызывать код адаптеров непосредственно из контроллера.
2) создай REST endpoint используй Spring Web REST Controller
3) напиши код адаптеров для вызова сервиса рекомендаций и сервиса игр с помощью RestClient или WebClient в блокирующем режиме
4) напиши код получения списка рекомендованных игр в контроллере - вызов адаптеров, маппинг полученных данных в модель, используемую в вашем API
5) создай заглушку для сервисов рекомендаций и игр, например, с помощью WireMock или mockwebserver. Заглушка не должна запускаться при промышленной эксплуатации, поэтому реализуй ее запуск под
   DEV-MODE профайлом Spring. Заглушку можно использовать как при отладке, так и для интеграционных тестов. Оффтоп: требования надежности особенно важны для сервисов в больших (enterprise) компаниях.
   Большая компания = много сервисов. В условиях господства микросервисной архитектуры у вашего сервиса скорее всего будет несколько сервисов-контрагентов. При этом нет возможности держать все эти
   сервисы в рабочем состоянии для отладки. А корректную работу вашего кода нужно подтвердить, причем в режиме, максимально приближенном к боевому. Поэтому приходится использовать заглушки.
6) напиши интеграционный тест, проверяющий успешный вызов нашего endpoint, используя Spring Test. Для тестирования вызова нашего сервиса можно использовать MockMvc, RestAssured или TestRestTemplate.
   Для приложений со сложной логикой основной упор нужно делать на написание unit тестов. Но паттерны надежности можно проверить с помощью интеграционных тестов.

## Задание 1. Оптимальное использование памяти

Приложение не должно использовать 100% оперативной памяти. Хотя в современном "облачном" мире (мире Docker-а) ваш процесс скорее всего будет единственным на сервере, выполняющим полезную работу,
должен оставаться резерв для системных процессов.
JVM делит используемую память на ряд областей, самой большой из которых является heap.

## Задание 3. Обработка ошибок

При работе любого приложения возникают исключения - Exceptions. Ошибки могут быть как в вашем коде, так и возникать при обращении к внешним сервисам. Исключения выглядят примерно так:
`
"status": 500,
"error": "Internal Server Error",
"trace": "org.springframework.web.reactive.function.client.WebClientResponseException: 200 OK from GET http://localhost:8090/recommendations/list, but response failed with cause: io.netty.handler.timeout.ReadTimeoutException
at org.springframework.web.reactive.function.client.WebClientResponseException.create(WebClientResponseException.java:337)
at org.springframework.web.reactive.function.client.DefaultClientResponse.lambda$createException$1(DefaultClientResponse.java:214)
at reactor.core.publisher.FluxMap$MapSubscriber.onNext(FluxMap.java:106)
`
На первый взгляд в данном ответе много полезной информации, даже stacktrace есть. Но она полезна разработчику. Потребитель нашего сервиса ее видеть не должен.
Второй важный момент - API должно быть предсказуемым, т.е. при любых исключениях ответы с информацией об ошибке должны быть единообразны.

### Контрольные вопросы

1. Почему потребитель нашего API не должен видеть имя исключения и stacktrace?
2. Как мы можем передать информацию об ошибке, возникшей при обработке запроса к нашему API, потребителю?
3. Какие средства для обработки ошибок предоставляет Spring Framework?

### Результат

1. Создай endpoint выбрасывающий исключение, посмотрите, какой ответ вернется клиенту
2. Исключи отображение в ответе информации, раскрывающей внутренности вашего сервиса
3. Продумай, как вы будете возвращать ошибки потребителю

## Задание 4. Timeouts

## Задание 5. Rate Limiter

Количество запросов к сервису может меняться со временем. Причиной может быть как поток новых клиентов после удачной рекламы, DDOS атака или даже ошибка в коде сайта или мобильного приложения.
Даже если запросы не вредоносные - не
всегда есть возможность масштабировать серверные мощности и обработать все поступившие запросы. В таком случае требуется настройка Rate Limiter. Важный момент - стоит дать знать клиенту, что его
запрос отбит Rate Limiter-ом. Рациональное поведение потребителя в этом случае - подождать некоторое время перед повтором.

### Контрольные вопросы

   секунды - тоже 10 запросов. Как отработает Rate Limiter? В каком случае мы можем пропустить такой всплеск запросов, в каком - должны отбить?
4. Как настроить Rate Limiter, если у нас максимально допустимая частота запросов 0.2 запроса в секунду?
5. Какой код ошибок HTTP используется для возврата ошибки клиенту при срабатывании Rate Limiter?
6. Предположим, вы предоставляете внешнее API с помощью API шлюза, который расположен перед вашим приложением. Где лучше разместить Rate Limiter? Плюсы и минусы обоих вариантов?
7. В каких еще случаях, кроме защиты от перегрузки сервера, может быть полезен Rate Limiter ?

### Результат

1. Выбери и добавь в проект библиотеку, обеспечивающую функционал Rate Limiter. Например, resilience4j
2. Установи ограничение числа запросов на метод контроллера
3. Напиши интеграционный тест, приводящий к срабатыванию Rate Limiter.
4. Проверьте, что часть запросов обработалась успешно, а по остальным вернулась ошибка. Проверьте код ошибки
5. Вынеси настройки Rate Limiter в файл с настройками Spring Boot

## Задание 6. Circuit Breaker

Сервис, с которыми мы взаимодействуем, может "упасть". Рассмотрим вариант, когда сервис-контрагент не отдает ошибку сразу, а просто ничего не возвращает. Мы настроили Timeout, будем ждать N секунд,
после чего
запрос отвалится по таймауту. Вроде бы все хорошо. Но если мы знаем по предыдущим неудачным запросам, что сервис не отвечает - мы могли бы не заставлять новых клиентов ждать. Более того - даже если
сервис отдает ошибку практически сразу - все равно мы тратим время на взаимодействие по сети, которое всегда на порядок дольше, чем вызов внутри программы. Второй важный момент -
пусть наш поставщик не упал, а еще жив, но "подтормаживает" - т.е. ему не хватает ресурсов, и он обрабатывает запросы сильно дольше, чем мы готовы ждать. В этом случае по-хорошему мы должны
дать ему восстановиться, а не "добивать" его запросами.
Все эти задачи решает Circuit Breaker.

### Контрольные вопросы

1. Для чего нужен Circuit Breaker? Почему этот паттерн так назвали?
2. Как работает Circuit Breaker?
3. Как обработать ситуацию, когда запрос не был отправлен к поставщику данных из-за срабатывания Circuit Breaker?
4. Как подобрать подходящие параметры Circuit Breaker?
5. Что будет, если мы установим слишком маленький порог срабатывания? Или слишком маленькое время ожидания?
6. Как лучше выставлять порог срабатывания - абсолютное значение или относительное?

### Результат

1. Выбери и добавь в проект библиотеку, обеспечивающую функционал Circuit Breaker. Например, resilience4j
2. Установи Circuit Breaker на метод вызова сервиса рекомендаций
3. Настрой заглушку так, чтобы сервис рекомендаций возвращал ошибку.
4. Напиши интеграционный тест, приводящий к срабатыванию Circuit Breaker. Убедитесь, что запросы в сервис рекомендаций не отправляются
5. Вынеси настройки Circuit Breaker в файл с настройками Spring Boot

## Задание 7. Retry

Как уже говорилось - сервисы, с которыми мы взаимодействуем, могут быть недоступны. Но не всегда ошибка при запросе к сервису говорит о том, что сервис не работает и нет смысла к нему обращаться в
ближайшее время. Это может быть временная проблема в сети, связанная, к примеру, с обновлением прокси-сервера. Или сработал Rate Limiter и конкретно запросу нашего сервиса не повезло. В таком случае
имеет смысл повторить запрос. Но не сразу, а спустя некоторое время. Время повтора с одной стороны ограничивается максимальным временем, в течение которого нам еще будет актуален результат. А с другой
стороны - минимальным временем, в течение которого проблема, вызвавшая временный сбой, исчезнет. Механизм повторов - Retry - можно реализовать самому, но зачем, когда для того есть готовые компоненты.

### Контрольные вопросы

1. Для чего нужен Retry?
2. Какие параметры мы можем настроить для алгоритма повторов?
3. Что такое exponential backoff? Сравните его с обычным повтором
4. Как выбрать минимальный интервал для начала повторов?
5. Почему важно ограничить число попыток?
6. При всех ли ошибках стоит использовать Retry? 403 forbidden? 429 Too Many Requests ?

### Результат

1. Выбери и добавь в проект библиотеку, реализующую механизм повторов. Подсказка - Spring Framework предоставляет такой функционал
2. Настрой повторы при возникновении ошибок при запросе к сервису рекомендаций
3. Настрой список ошибок, при которых будет срабатывать Retry
4. Настрой заглушку так, чтобы сервис рекомендаций возвращал 2 ошибки, а потом - успешный ответ.
5. Напиши интеграционный тест, приводящий к запуску повторов
6. Убедись, что с третьей попытки получен успешный ответ
7. Вынеси настройки Retry в файл с настройками Spring Boot

## Задание 8. Fallback

Снова поговорим о сбоях. Предположим, наш сервис не смог обработать запрос клиента. Это может быть связано как с ошибкой в нашем сервисе, так и со сбоем смежника. Что делать в таком случае? Самый
простой вариант - вернуть ошибку. Но всегда ли ошибка - единственный возможный ответ? Нет ли случаев, когда мы можем вернуть клиенту частичный ответ? Или взять ответ из кэша? Или хотя бы вернуть
рекомендации по дальнейшим действиям? Именно это и реализует паттерн Fallback

### Контрольные вопросы

1. Для чего нужен Fallback?
2. Что можно вернуть клиенту при отсутствии актуальных данных?
3. В каких случаях нельзя вернуть клиенту альтернативный содержательный ответ вместо ошибки?

### Результат

1. Изучи, как реализован fallback механизм в Spring Retry и resilience4j
2. Реализуй fallback ответ в виде возврата рекомендации по умолчанию при падении сервиса рекомендаций
3. Настройки для рекомендации по умолчанию вынеси в файл с настройками Spring Boot
4. Добавь возможность отключения Fallback ответа, вынеси рубильник в файл настроек Spring Boot

## Задание 9. Cache

Часто запросы клиентов повторяются. Клиент может неосознанно или даже сознательно нажать на кнопку "Обновить". Или ответ может быть одинаковым для разных клиентов. Имеет ли смысл в этом случае всегда
обращаться к сервису-контрагенту за данными? Ведь эти данные скорее всего хранятся в БД, а запрос к БД - это "тяжелый" запрос, лишних запросов к БД стоит избегать. И как говорилось ранее - запрос по
сети - это всегда лишняя задержка. Другая сторона медали - полученный ответ может быть актуален спустя секунду или даже в ближайшие 10 минут, но не факт, что он будет актуален через час. Избавится
от
лишних запросов можно с помощью кэширования данных (cache)

### Контрольные вопросы

1. Для чего нужно кэширование?
2. Какие риски несет кэширование? Как бороться с этими рисками?
3. Какие данные стоит кэшировать? Рекомендации? Курс валют? Цену на товар?
4. Как связано кэширование с реализацией паттерна Fallback?
5. В чем разница между локальным и распределенным кэшом? В чем их плюсы и минусы?
6. От чего зависит величина TTL (Time To Live) для записи в кэше?

### Результат

1. Выбери и подключи библиотеку, реализующую локальное кэширование (для простоты в этом проекте мы реализуем локальный кэш). Важным преимуществом библиотеки в нашем случае является простота ее
   интеграции с механизмом кэширования Spring Boot, как, например, у Caffeine
2. Реализуй кэширование ответов сервиса с информацией об играх
3. Настрой заглушку, чтобы она вернула один успешный ответ с информацией по игре, а далее возвращала ошибочные
4. Напиши интеграционный тест
5. Убедись, что даже при ошибках от сервиса, информация об игре возвращается
6. Настой параметры кэширования - TTL и объем используемой памяти
7. Вынеси эти настройки в файл с настройками Spring Boot
