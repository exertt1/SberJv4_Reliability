## Введение

При создании приложения для миллионов пользователей, обрабатывающего десятки или даже тысячи запросов в секунду, нужно соблюдать ряд требований. Данные требования позволяют достичь следующих целей:

1. Не «упасть» при неожиданном повышении нагрузки — числа входящих запросов.
2. Не «положить» смежные сервисы — поставщики данных, не создавать лишнюю нагрузку на систему в целом.
3. Вернуть осмысленный ответ клиенту даже в случае сбоя.
4. Обработать максимальное число пользовательских запросов на имеющемся «железе».

Назовем эти требования паттернами надежности. Вот их список:

1. оптимальное использование памяти;
2. пул потоков;
3. обработка ошибок;
4. Timeouts;
5. Rate Limiter;
6. Circuit Breaker;
7. Retry;
8. Fallback;
9. Cache.

Материалы к заданиям можно найти [тут](materials/links.md).

### Общие замечания

#### Тестирование паттернов

Некоторые паттерны для проверки работы вручную или через тест требуют метода в классе REST-контроллера. Рекомендуется для каждого паттерна делать отдельный метод. Так можно избежать их взаимного влияния и упростить тестирование. Но так как в реальной жизни бизнес-операция для выполнения требований надежности может потребовать настройки нескольких паттернов, такую реализацию предлагается сделать и протестировать на отдельном методе как «задачу со звездочкой».

#### Версии библиотек

В задании не указываются конкретные версии библиотек, т. к. со временем любая версия устареет. Это справедливо всегда, кроме тех случаев, когда самостоятельный подбор работающей версии занимает много времени. Рекомендации актуальны на 2025 год.

## Задание 0.5. Тестовый бизнес-сервис

Суть проекта — вернуть клиенту список рекомендованных игр по REST API. Для получения списка используются 2 внешних вызова по REST:

1. вызов сервиса рекомендаций, в ответ возвращается список id игр;
2. вызов сервиса игр для получения данных об игре по id, полученным от сервиса рекомендаций.

### Основные шаги

1) Создай структуру проекта с разделением по разным пакетам слоя представления (web) и слоя адаптеров к внешним сервисам (adapter). Модель можно не выносить в отдельный корневой пакет, т. к. наш тестовый сервис не содержит много бизнес-логики. Можно обойтись паттерном Transaction Script и вызывать код адаптеров непосредственно из контроллера. 
    
    Возможную схему пакетов можно посмотреть в `arch.plantuml`. Слой mapper опционален и может быть полезен при преобразовании DTO, полученных из слоя адаптеров.

2) Создай REST endpoint, используй Spring Web REST Controller.
3) Напиши код адаптеров для вызова сервиса рекомендаций и сервиса игр с помощью RestClient или WebClient в блокирующем режиме.
4) Напиши код получения списка рекомендованных игр в контроллере: вызов адаптеров, маппинг полученных данных в модель, используемую в твоем API.
5) Создай заглушку для сервисов рекомендаций и игр, например, с помощью WireMock или mockwebserver. 

    Рекомендуемые версии библиотек: «com.github.tomakehurst:wiremock-standalone:3.0.1» и «com.squareup.okhttp3:mockwebserver:4.12.0». Заглушка не должна запускаться при промышленной эксплуатации, поэтому реализуй ее запуск под DEV-MODE профайлом Spring. Заглушку можно использовать как при отладке, так и для интеграционных тестов. 
    
    _Оффтоп: требования надежности особенно важны для сервисов в больших (enterprise) компаниях. Большая компания = много сервисов. В условиях господства микросервисной архитектуры у твоего сервиса, скорее всего, будет несколько сервисов-контрагентов. При этом нет возможности держать все эти сервисы в рабочем состоянии для отладки. А корректную работу твоего кода нужно подтвердить, причем в режиме, максимально приближенном к боевому. Поэтому приходится использовать заглушки._

6) Используя Spring Test, напиши интеграционный тест, проверяющий успешный вызов нашего endpoint. Для тестирования вызова нашего сервиса можно использовать MockMvc, RestAssured или TestRestTemplate. 

    Для приложений со сложной логикой основной упор нужно делать на написание unit-тестов. Но паттерны надежности можно проверить с помощью интеграционных тестов.

## Задание 2. Пул потоков

С твоим приложением могут работать десятки, сотни или тысячи клиентов одновременно. Можно было бы поставить всех в очередь, но это очень долго. Java позволяет выполнять задачи параллельно в разных потоках. Но сколько этих потоков нужно? Как сопоставить поток клиентскому запросу? Реализация многопоточности — не самая простая задача. К счастью, в большинстве случаев тебе это делать не придется. Tomcat — контейнер сервлетов, используемый в Spring Boot по умолчанию для обработки HTTP-запросов, уже включает в себя пул потоков. Нужно лишь его настроить.

### Контрольные вопросы

1. Для чего нужен пул потоков? Чем он лучше простого создания потоков по необходимости?
2. Как настроить число потоков, обрабатывающих входящие запросы, в Tomcat?
3. Что происходит с потоками, когда нет входящих запросов?
4. Что происходит с потоками, когда число входящих запросов превышает число потоков в пуле?
5. Как выяснить оптимальное число потоков? Какие факторы на это влияют?

### Результат

1) Установи ограничение на максимальное число потоков, число потоков, постоянно находящихся в пуле, и размер очереди запросов.
2) Выбери и установи утилиту, позволяющую произвести нагрузочное тестирование локально, например, JMeter или Apache Benchmark. Сохрани конфигурацию ее запуска в корне проекта. 
3) Убедись, что ограничение по числу потоков работает.

## Задание 3. Обработка ошибок

При работе любого приложения возникают исключения — Exceptions. Ошибки могут быть как в твоем коде, так и возникать при обращении к внешним сервисам. Исключения выглядят примерно так:

`
"status": 500,
"error": "Internal Server Error",
"trace": "org.springframework.web.reactive.function.client.WebClientResponseException: 200 OK from GET http://localhost:8090/recommendations/list, but response failed with cause: io.netty.handler.timeout.ReadTimeoutException
at org.springframework.web.reactive.function.client.WebClientResponseException.create(WebClientResponseException.java:337)
at org.springframework.web.reactive.function.client.DefaultClientResponse.lambda$createException$1(DefaultClientResponse.java:214)
at reactor.core.publisher.FluxMap$MapSubscriber.onNext(FluxMap.java:106)
`

На первый взгляд в данном ответе много полезной информации, даже stacktrace есть. Но она полезна разработчику. Потребитель нашего сервиса ее видеть не должен. Второй важный момент — API должно быть предсказуемым, т. е. при любых исключениях ответы с информацией об ошибке должны быть единообразны.

### Контрольные вопросы

1. Почему потребитель нашего API не должен видеть имя исключения и stacktrace?
2. Как мы можем передать потребителю информацию об ошибке, возникшей при обработке запроса к нашему API?
3. Какие средства для обработки ошибок предоставляет Spring Framework?

### Результат

1) Создай endpoint, выбрасывающий исключение, и посмотри, какой ответ вернется клиенту.
2) Исключи отображение в ответе информации, раскрывающей внутренности твоего сервиса.
3) Продумай, как ты будешь возвращать ошибки потребителю.
4) Напиши тест, проверяющий успешный вызов и вызов с ошибкой.

## Задание 4. Timeouts

Обработка запроса клиента занимает некоторое время. Иногда это время может быть больше, чем мы ожидаем. При этом наш потребитель, как правило, не готов ждать долго, чтобы получить запрошенную информацию. 

Представь ситуацию: сервис-поставщик начинает долго отвечать, соответственно, обработка запроса нашим сервисом занимает больше времени, часть клиентов, не дождавшись ответа, закрывает сайт или приложение, в то время как нам приходят запросы от новых клиентов.

### Контрольные вопросы

1. Чем отличается connection timeout от request timeout?
2. К чему может привести ситуация, когда таймаут очень большой или, что еще хуже, не ограничен?
3. Как настроить таймауты для выбранного тобой ранее HTTP-клиента?
4. Можно ли настроить таймаут для endpoint? Где это лучше сделать: в нашем сервисе или на прокси-сервере перед ним?
5. Как должны соотноситься таймаут для входящего запроса к нашему сервису и таймауты на запросы к сервисам-поставщикам данных?
6. Подумай, как определить оптимальную величину таймаута? Предупреждение: однозначного ответа на этот вопрос нет.

### Результат

1) Явно настрой connection timeout и request timeout для выбранного HTTP-клиента.
2) Вынеси настройки таймаута в файл с настройками Spring Boot, это упростит их изменение в будущем.
3) Сэмулируй долгий ответ одного из своих сервисов-поставщиков.
4) Пробрось информацию об ошибке таймаута с учетом знаний из предыдущего задания.
5) Напиши интеграционный тест, проверяющий данный кейс.

## Задание 5. Rate Limiter

Количество запросов к сервису может меняться со временем. Причиной может быть поток новых клиентов после удачной рекламы, DDoS-атака или даже ошибка в коде сайта или мобильного приложения. Даже если запросы не вредоносные, не всегда есть возможность масштабировать серверные мощности и обработать все поступившие запросы. В таком случае требуется настройка Rate Limiter. 

_Важный момент: стоит дать знать клиенту, что его запрос отбит Rate Limiter. Рациональное поведение потребителя в этом случае — подождать некоторое время перед повтором._

### Контрольные вопросы

1. Для чего нужен Rate Limiter?
2. Почему лучше «отбить» часть запросов клиентов, чем попытаться обработать все?
3. Предположим, Rate Limiter настроен с периодом 1 секунда и rate, равным 10. Рассмотрим интервал 2 секунды. Пусть за последние 100 мс первой секунды к нам пришло 10 запросов, и в первые 100 мс второй секунды — еще 10 запросов. Как отработает Rate Limiter? В каком случае мы можем пропустить такой всплеск запросов, а в каком должны отбить?
4. Как настроить Rate Limiter, если у нас максимально допустимая частота запросов 0.2 запроса в секунду?
5. Какой код ошибок HTTP используется для возврата ошибки клиенту при срабатывании Rate Limiter?
6. Предположим, ты предоставляешь внешнее API с помощью API-шлюза, который расположен перед твоим приложением. Где лучше разместить Rate Limiter? Плюсы и минусы обоих вариантов?
7. В каких еще случаях, кроме защиты от перегрузки сервера, может быть полезен Rate Limiter?

### Результат

1) Выбери и добавь в проект библиотеку, обеспечивающую функционал Rate Limiter. Например, resilience4j.
2) Установи ограничение числа запросов на метод контроллера.
3) Напиши интеграционный тест, приводящий к срабатыванию Rate Limiter.
4) Проверь, что часть запросов обработалась успешно, а по остальным вернулась ошибка. Проверь код ошибки.
5) Вынеси настройки Rate Limiter в файл с настройками Spring Boot.

## Задание 6. Circuit Breaker

Сервис, с которым мы взаимодействуем, может «упасть». Рассмотрим вариант, когда сервис-контрагент не отдает ошибку сразу, а просто ничего не возвращает. 

Мы настроили Timeout, будем ждать N секунд, после чего запрос отвалится по таймауту. Вроде бы все хорошо. Но если мы знаем по предыдущим неудачным запросам, что сервис не отвечает, мы могли бы не заставлять новых клиентов ждать. Более того, даже если сервис отдает ошибку практически сразу, все равно мы тратим время на взаимодействие по сети, которое всегда на порядок дольше, чем вызов внутри программы. 

Второй важный момент — пусть наш поставщик не упал, а еще жив, но «подтормаживает», т. е. ему не хватает ресурсов, и он обрабатывает запросы сильно дольше, чем мы готовы ждать. В этом случае по-хорошему мы должны дать ему восстановиться, а не «добивать» его запросами. Все эти задачи решает Circuit Breaker.

## Задание 7. Retry

Как уже говорилось, сервисы, с которыми мы взаимодействуем, могут быть недоступны. Но не всегда ошибка при запросе к сервису говорит о том, что сервис не работает и нет смысла к нему обращаться в ближайшее время. Это может быть временная проблема в сети, связанная, к примеру, с обновлением прокси-сервера. Или сработал Rate Limiter, и конкретно запросу нашего сервиса не повезло. 

В таком случае имеет смысл повторить запрос. Но не сразу, а спустя некоторое время. Время повтора, с одной стороны, ограничивается максимальным временем, в течение которого нам еще будет актуален результат. А с другой стороны — минимальным временем, в течение которого проблема, вызвавшая временный сбой, исчезнет. 

Механизм повторов — Retry — можно реализовать самому, но зачем, когда для того есть готовые компоненты.

## Задание 9. Cache

Часто запросы клиентов повторяются. Клиент может неосознанно или даже сознательно нажать на кнопку «Обновить». Или ответ может быть одинаковым для разных клиентов. Имеет ли смысл в этом случае всегда обращаться к сервису-контрагенту за данными? Ведь эти данные, скорее всего, хранятся в БД, а запрос к БД — это «тяжелый» запрос, и лишних запросов к БД стоит избегать. И как говорилось ранее, запрос по сети — это всегда лишняя задержка. Другая сторона медали — полученный ответ может быть актуален спустя секунду или даже в ближайшие 10 минут, но не факт, что он будет актуален через час. Избавиться от лишних запросов можно с помощью кеширования данных (cache).
